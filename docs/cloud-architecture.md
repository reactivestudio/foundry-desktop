# foundry-cloud: архитектура облачной части

Черновик. Код не начат; реализуется отдельным проектом.

Дополняет [модель данных](data-model.md) (какие данные бывают) и
[наблюдаемость](observability.md) (кто их пишет и куда). Здесь — устройство
облачного сервиса: контексты, их язык, границы, хранилище и протокол с машиной
разработчика.

## Что меняется по сравнению с наблюдаемостью

Спека наблюдаемости писалась под настольное приложение, где источник правды —
`.foundry` на машине. С появлением облака источник правды переезжает:

| | Было | Стало |
|---|---|---|
| Правда о задаче и артефактах | `.foundry` на машине | **`foundry-cloud`** |
| Локальный журнал | источник истины | **спул**: буфер на время работы и на случай обрыва связи |
| Ревью | в приложении | **в вебе**, до коммита |
| Машина | хранит историю | **исполняет и забывает** |

---

# 1. Границы: что облако делает и чего не делает

**Делает:** держит задачи и их движение по пайплайну, раздаёт работу раннерам,
хранит все артефакты и изменения кода, показывает ревью, считает деньги, ведёт
подписки, копит датасет для обучения агентов и скиллов.

**Не делает:**

- **не запускает агента** — Claude Code живёт на машине разработчика;
- **не видит git** — ни удалённого репозитория, ни доступа к нему: ревью
  проводится **до коммита**;
- **не хранит репозиторий** — только тела тронутых файлов;
- **не хранит ключ Anthropic** — за токены платит пользователь напрямую;
- **не инициирует соединение к машине** — связь всегда исходящая от раннера.

Мы продаём пайплайн, историю, ревью, командную работу и аналитику — не инференс.

# 2. Процессы

```
   foundry-web ─┐                                ┌── Postgres
foundry-desktop ─┼── REST + SSE ──▶ foundry-cloud ┼── объектное хранилище
   foundry-cli ─┘                       ▲        └── Redis
                                        │ gRPC-стрим (исходящий)
                              foundry-runtime (Go, на машине)
                                        │
                                        ├──▶ Claude Code (харнес)
                                        └──▶ рабочая копия проекта
```

| Процесс | Что это |
|---|---|
| `foundry-cloud` | Kotlin + Spring Boot, модульный монолит по контекстам |
| `foundry-runtime` | Go-раннер на машине: исполняет назначения, считает гейты, шлёт факты |
| `foundry-web` | веб-интерфейс: доска, стадии, ревью артефактов и изменений кода |
| `foundry-desktop`, `foundry-cli` | те же клиенты того же API |

Инфраструктура: PostgreSQL (состояние и журнал), объектное хранилище с
S3-совместимым API (тела файлов), Redis (живая лента в браузер, аренды).

Объектное хранилище прячется за адаптером. На старте реализация — файловая
система с ключом `sha256`; при росте — Garage или SeaweedFS; переезд = скопировать
дерево объектов.

# 3. Контексты

Режем по языку и владению состоянием, не по механизмам. Правило именования — как
в desktop: единственное число, центральное понятие контекста.

## Ядро

| Контекст | Владеет | Язык |
|---|---|---|
| **`Task`** | Task, Request, Assignment, Phase, конверт, результат гейта, переходы, возвраты | задача, назначение, стадия, конверт, гейт, возврат |
| **`Review`** | Review, Comment, Finding, бриф доработки, оценка судьи и вердикт человека | замечание, принято, вернуть, устарел, порог |
| **`Pipeline`** | Pipeline, Stage, GateSpec, ростер агентов, `Skill@version`, шаблоны промптов, тир-лист моделей | сценарий, стадия, гейт, скилл, тир |

## Поддерживающие

| Контекст | Владеет | Почему отдельно |
|---|---|---|
| **`Artifact`** | Artifact и ревизии, Changeset, тела по хэшу, вычисление диффа | предмет, а не процесс; единственный, кто знает про объектное хранилище |
| **`Runner`** | раннеры, аренда, очередь назначений, стрим, heartbeat | «где исполняется», а не «что исполняется»; единственный держатель долгих соединений |
| **`Journal`** | события, секции, ретенция, свёртки | пишется потоком и только дополняется; профиль нагрузки чужой всем |
| **`Cost`** | расход токенов, цены моделей, свёртки снизу вверх | деньги считаются из журнала; цена — не свойство сценария |

## Универсальные

`Account` (организация, участник, роль, токены раннеров) · `Subscription`
(тариф, квоты, счета) · `Notification` (почта, вебхуки, пуши).

## Связи

```
        Pipeline ──────────┐  правила читают все, пишет только человек
                           ▼
   Runner ──событиями──▶ Task ◀──событиями── Review
                           │                    ▲
                           ▼                    │ changeset готов
                        Journal ──▶ Cost     Artifact
```

Правила связей:

1. **Синхронно — только вниз**: `Task` читает `Pipeline`, чтобы взять снимок
   конфигурации в момент старта стадии. Всё остальное — доменные события.
2. **Состояние задачи меняет только `Task`.** `Review` публикует вердикт,
   `Runner` публикует факт исполнения; решение о переходе принимает `Task`.
3. **`Pipeline` и `Journal` ни от кого не зависят** — циклов в графе нет.
4. Чужие агрегаты не читаются напрямую: либо публичный интерфейс приложения,
   либо собственная проекция, собранная из событий.

## Принятые решения по спорным местам

- **`Review` — отдельный контекст, не часть `Task`.** У приёмки свой язык, свой
  темп (человек читает часами) и свой рост (треды, упоминания, привязка к
  строкам). Переиграть = свернуть в `Task`, если ревью навсегда останется
  «принял/вернул».
- **Судья-агент расщеплён**: его *исполнение* — обычная стадия, значит `Task`;
  его *оценка с порогом и замечаниями* — `Review`. Тогда судья и человек говорят
  на одном языке и производят один тип замечания.
- **Гейт остаётся в `Task`**: это детерминированное постусловие перехода, то есть
  его собственное решение, а не чужое суждение.

# 4. Устройство сервиса

- **Пакет на контекст**, внутри слои `domain / application / infrastructure /
  api`. Контекст сверху, слои папками внутри — как в desktop.
- **Между контекстами — только доменные события** и публичные интерфейсы
  приложения. Ни одного обращения к чужому репозиторию.
- **Схема базы на контекст**, одна инстанция Postgres. Никаких join'ов через
  границу и никаких внешних ключей между схемами — это и есть будущий шов.
- **Transactional outbox с первого дня.** Внутри процесса это таблица и локальный
  диспетчер; при выносе контекста в сервис ничего переписывать не надо.
- **Идемпотентность на приёме**: ключ `eventId` и таблица обработанных.
- Миграции — Flyway, по схеме на контекст.

**Повышение до отдельного сервиса — по заслугам, а не по плану.** Кандидаты по
порядку: `Runner` (тысячи долгих соединений), `Journal` (запись потоком),
`Cost`/аналитика (другой профиль запросов).

# 5. Хранилище

| Данные | Где | Почему |
|---|---|---|
| Состояние: задачи, назначения, стадии, гейты, ревью, замечания, комментарии | PostgreSQL | связи, транзакции, выборки по многим осям |
| Тела: файлы до/после, артефакты, патчи, транскрипты | объектное хранилище, ключ `sha256` | неизменяемы, крупные, читаются редко, дедуп |
| Журнал событий | PostgreSQL, секции по времени + BRIN | пишется потоком, читается диапазоном |
| Живая лента в браузер | Redis pub/sub → SSE | доставка, а не хранение |
| Датасет для обучения | экспорт в Parquet | другой профиль нагрузки, копится годами |

## Blob, адресуемый содержимым

Ключ blob'а — `sha256` от содержимого. Что это даёт:

- **дедуп**: второй заход тронул 2 файла из 8 — приезжают 2 новых blob'а;
- **иммутабельность**: кэшируется вечно, `ETag` — сам хэш;
- **проверяемость**: совпал хэш — это ровно та версия, которую ревьюили.

## Эскиз таблиц

```
account.member(id, org_id, email, role)
pipeline.stage(id, pipeline_id, position, name, agent_ref, model_tier)
pipeline.gate_spec(id, stage_id, kind, params jsonb)

task.task(id, org_id, key, title, status, pipeline_id, created_at)
task.assignment(id, task_id, actor_ref, status, predecessor_id)
task.phase(id, assignment_id, stage_ref, attempt, status, config_snapshot jsonb)
task.gate_result(id, phase_id, spec_ref, verdict, evidence jsonb)

artifact.blob(sha PRIMARY KEY, size, encoding, uri, is_binary)
artifact.artifact(id, phase_id, path, role, revision, blob_sha → blob)
artifact.changeset(id, phase_id, revision, base_commit, created_at)
artifact.changeset_file(changeset_id, path, status, blob_before, blob_after)

review.review(id, phase_id, changeset_id, state, decided_by, decided_at)
review.comment(id, review_id, path, side, line, anchor_sha, body, author)
review.finding(id, review_id, path, line, severity, body, resolved_by)

journal.event(id, occurred_at, assignment_id, phase_id, kind, payload jsonb)
        └─ PARTITION BY RANGE (occurred_at)

cost.usage(phase_id, model_ref, input, output, thinking, cache_read, cache_write)
cost.model_price(model_ref, valid_from, input_price, output_price, cache_price)
```

`changeset_file` не хранит ни строчки текста — только два хэша. Тяжесть в
объектном хранилище, база тонкая.

**`tenant_id`/`org_id` — в каждой таблице с первого дня.** Добавить потом = миграция
всего.

# 6. Протокол с раннером

## Соединение

- Раннер сам открывает **исходящий gRPC-стрим** (двунаправленный) к `Runner`.
  Веб-сокет — запасной путь для сетей, где gRPC режут.
- Аутентификация: долгоживущий токен раннера меняется на короткий JWT.
- Никаких входящих соединений в сеть пользователя.

## Аренда, а не «взял в работу»

Назначение выдаётся под **аренду** с продлением по heartbeat. Раннер пропал —
аренда истекла — назначение вернулось в очередь. Иначе задачи зависают навсегда.

## Ход одной стадии

1. Раннер: «свободен». `Runner` выдаёт назначение со снимком конфигурации.
2. Раннер запускает Claude Code **как дочерний процесс** — он не наблюдает за
   агентом со стороны, а держит его.
3. События идут пачками наверх по тому же стриму; параллельно пишутся в локальный
   спул на диск.
4. Гейты считает **раннер** — файлы у него. Наверх едет вердикт с доказательством.
5. Тела: сначала переговоры по хэшам («какие из этих sha у вас есть?»), затем
   **presigned PUT напрямую в хранилище**, мимо приложения. Потом сообщение
   `Artifact`: «принял, вот sha».
6. Раннер сообщает итог стадии; `Task` решает, что дальше.

## Офлайн

Раннер обязан работать без сети: взятые назначения исполняются, события копятся в
спуле, при появлении связи досылаются по `seq`. Обрыв связи не должен убивать
сеанс.

# 7. Ревью до коммита

Главное ограничение продукта: **ревью проводится до того, как что-либо
закоммичено**, и облако не имеет доступа к git.

## Changeset — это артефакт стадии

Раннер собирает самодостаточный пакет:

```
changeset:
  baseCommit: a1b2c3d          ← против чего смотрим (HEAD, никуда не пушится)
  patch:      unified diff     ← git diff HEAD, целиком текстом
  files:
    - path, status (modified|added|deleted|renamed)
      before: тело из HEAD     ← blob
      after:  тело из рабочей копии
```

## Дифф не хранится — он вычисляется

Хранятся **два тела**. Дифф считается при показе, а «раскрыть контекст выше/ниже/
весь файл» — это нарезка строк из тела, которое уже есть. Раскрытие бесконечно и
бесплатно, но только по тронутым файлам: ревьюят изменения, а не репозиторий.

## Грабли, которые обязаны быть учтены

- **Новые файлы `git diff` не показывает** — нужен `git add --intent-to-add`
  либо отдельный сбор untracked. Самая частая причина «агент сделал, а в ревью
  пусто».
- **Файл уезжает под ногами** — снимок делается `git stash create` (или
  `git write-tree`): фиксирует рабочую копию объектом, не трогая ветку.
- **Бинарники и гиганты** — тело не грузим: имя, размер, хэш, пометка.
- **Переименования и удаления** — рендер обязан их различать, иначе покажет
  «удалил 300 строк, добавил 300».
- **Секреты** — чистка на записи, до отправки. Раз тела уезжают в облако,
  редакция обязательна, а не опциональна.

## Комментарии и повторный заход

Комментарий привязан к `(путь, сторона, строка, хэш тела)`. Приехала ревизия 2:
тело не изменилось — комментарий на месте; изменилось — перепривязка по
окружающим строкам, не вышло — «устарел».

## После вердикта

- **Принял** → `Task` двигает стадию дальше; коммит делает раннер **после**
  ревью, локально. Пушить или нет — отдельное решение пользователя.
- **Вернул** → комментарии становятся `Finding` с адресом → `Task` заводит новое
  назначение с брифом доработки (возврат не воскрешает старое, см. модель данных).

# 8. Приватность, ретенция, тарифы

- **Локально пишем всё, наверх — по выбранному уровню.** Уровни детализации
  становятся тарифными: только числа → плюс дифф → плюс полные тела промптов и
  артефактов.
- **Код целиком не уезжает никогда** — только тела тронутых файлов.
- **Ключ Anthropic не уезжает никогда.**
- **Ретенция раздельная**: тела старых ревизий чистятся по возрасту, свёртки
  (стадии, деньги, вердикты) живут вечно — они крошечные.
- **Транскрипт агента — blob**, а не строки в базе: он единственный, что реально
  растёт.

---

# 9. Наблюдаемость самого облака

Один `traceId` от нажатия в вебе до строки в журнале раннера — иначе распределённую
цепочку не отладить. Поля именуются по соглашению OpenTelemetry `gen_ai.*`;
соответствие понятий: назначение — трасса, стадия — спан, вызов инструмента —
вложенный спан. Экспорт в OTLP — опция, не фундамент.

# 10. Порядок работ

1. **Скелет**: `Account`, `Pipeline`, `Task` со статусами, миграции, схемы на
   контекст, outbox.
2. **Раннер и стрим**: `Runner`, аренда, heartbeat, запуск Claude Code, события в
   `Journal`.
3. **Предметы**: `Artifact` — blob'ы, переговоры по хэшам, presigned-загрузка,
   changeset.
4. **Ревью**: `Review` — дифф из двух тел, комментарии, замечания, вердикт,
   возврат.
5. **Деньги**: `Cost` — расход из журнала, цены, свёртки; затем `Subscription`.
6. **Датасет**: экспорт, отложенный исход, `Insight`.

# 11. Открытые вопросы

- Хостед-раннер: когда предлагать исполнение в нашей песочнице (клон репозитория
  у нас) как второй режим того же пайплайна.
- Что делать с задачей, начатой вне наших интерфейсов (человек запустил Claude
  Code сам): как склеивать — по каталогу, по ветке или по сессии харнеса.
- Порог размера changeset, после которого тела грузятся по требованию, а не сразу.
- Нужен ли `Project` собственным агрегатом (свой ростер, свои гейты) или это
  ссылка — вопрос переехал из модели данных и здесь не решён.
- Многопользовательское ревью: сколько аппрувов требуется и кто может отклонить
  замечание судьи.
- Где живёт реестр цен моделей, если тир-лист в `Pipeline`, а цены в `Cost`:
  дублировать ссылку или держать модель справочником в `Cost`.
